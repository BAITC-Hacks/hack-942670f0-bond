# ВЕРШИНА (Vertex)

**Восстановление финансовой структуры организованной группы по транзакционной сети.**
Кейс «Граф денег» · HackAlem AI · заказчик Freedom.

> AML-аналитик видит только низ цепочки — дропов. «Вершина» разворачивает граф на 4 колена вверх,
> присваивает каждому участнику **роль по формальному правилу с порогом**, группирует сеть в кластеры
> и выдаёт **ранжированный список «кого проверять первым»** — с числовым обоснованием на каждый gid.

## Принцип: никаких чёрных ящиков

Каждая роль — это **правило с порогом**, а не «модель так решила». Пороги **вычисляются из данных**
(перцентили распределений), а не зашиты числами — их видно в консоли при запуске и в `out/summary.json`.
Всё детерминировано (`seed=42`), считается локально за секунды, без облака/GPU/платных сервисов.

### Словарь ролей и правила

| Роль | Смысл | Правило (порог) | Кол-во |
|---|---|---|---:|
| **coordinator** | координатор, кандидат в организаторы | `betweenness ≥ p98` **и** `pagerank ≥ p90` **и** есть вход и выход (узел-«мост») | 13 |
| **distributor** | веерная рассылка на многих | `out_deg ≥ p95(≈16)` **или** (`out_deg ≥ 5` и `out_kzt ≥ p90`), при `out_deg ≥ in_deg` | 99 |
| **consolidator** | собирает от многих | `in_deg ≥ 3` при `in_deg ≥ out_deg` | 136 |
| **transit** | проводит деньги насквозь (мул/layering) | есть вход и выход, `0.7 ≤ pass_through ≤ 1.3` (не-seed); остаток двустороннего потока при `pass_through ≥ 0.5` | 324 |
| **terminal** | деньги пришли и осели | `out_deg = 0` и `in_deg ≥ 1` | 1483 |
| **peripheral** | признаков роли нет | всё остальное (изолированные, слабые, удерживающие без структуры) | 193 |

Почему именно эти метрики:
- **PageRank** (взвешенный по сумме) — куда «стекается» влияние денег.
- **HITS**: `authority` = кому шлют многие (сигнал **сборщика**), `hub` = кто шлёт многим (сигнал **распределителя**) — алгоритм буквально разделяет источники и накопители.
- **Betweenness** — кто сидит «между» потоками. Высокая брокерность + вес = **координатор**.
- **pass_through = out_kzt / in_kzt** — доля полученного, ушедшая дальше. ≈1 → деньги не задерживаются (транзит).
- **simple_cycles (≤5)** — возвратные потоки, классический признак layering (300 узлов в циклах).

### Приоритет проверки (кого первым)

```
priority = 0.30·вес_роли + 0.20·rank(pagerank) + 0.20·rank(betweenness)
         + 0.15·rank(оборот) + 0.08·(seed_плательщиков/3) + 0.07·[в цикле]
```
затем min-max в диапазон 0..1. Вес роли: координатор 1.0 → сборщик 0.85 → распределитель 0.75 →
транзит 0.55 → терминал 0.40 → периферия 0.10.

## Четыре ловушки кейса — как обработаны

1. **`out_deg == 0` ≠ «деньги осели».** 444 узла на 4-м колене — это обрыв обхода, а не сток.
   Они помечены флагом `truncated_by_depth`, получают роль `terminal` со **сниженной уверенностью (0.35)**
   и честным evidence: *«обрезан 4-м коленом — исход не наблюдаем, статус не подтверждён»*.
   Настоящих терминалов (глубина <4, исходящих нет) — 1042.
2. **У seed занижен `in_kzt`.** Граф собран *от* seed по исходящим, входящие извне не видны
   (медиана `pass_through` у seed ≈ 0.86, но встречается 20+). Для seed роль `consolidator` опирается
   на `in_deg` (структуру), а не на сумму; из `transit`-по-pass_through seed исключены; в evidence сумму для seed не показываем.
3. **Сумма ≠ количество.** Один перевод на 4 млн и сорок по 100 тыс. дают одинаковый `in_kzt`.
   В evidence всегда обе величины (`…₸ за N перев.`), распределитель учитывает и `out_deg`, и `out_kzt`.
4. **Граф направленный и взвешенный.** Все центральности считаются на ориентированном взвешенном графе.
   Кластеризация Louvain работает на **неориентированной взвешенной проекции** — это **оговорено явно**
   (направление там теряется намеренно, для выделения сообществ).

## Схема выгрузок

**nodes_roles.csv** (2 248 строк): `gid, role, role_score, cluster_id, priority_score, evidence,`
`in_deg, out_deg, in_kzt, out_kzt, pagerank, pass_through, depth, is_seed, truncated_by_depth` +
доп. прозрачные метрики: `hub, authority, betweenness, net_kzt, n_seed_in, in_cycle, turnover_days`.
`evidence` — до 200 символов, всегда с числами.

**clusters.csv**: `cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis`.
Гипотеза генерируется из состава ролей кластера (пирамида сбора / веерная рассылка / транзитная цепочка / …).

**top_nodes.csv**: `rank, gid, role, priority_score, why` — ≥20 строк (у нас 30).

## Дашборд `out/vertex.html`

- Направленный граф: **цвет = роль**, **размер = приоритет**, **стрелка = направление денег**, кольцо = seed.
- Слева: легенда-фильтр по ролям, слайдер приоритета, выбор кластера, поиск по gid, список «кого проверять первым».
- **🎯 Фокус: топ-30** — изолирует топ-узлы и их окружение (чистая структура схемы для показа).
- Клик по узлу → панель: роль, приоритет, обороты, **обоснование** и списки «платят ему» / «платит он».

## Что можно улучшить дальше (честные ограничения)

- Нет ground-truth ролей — оцениваем обоснованность критериев, а не точность (так и задумано в кейсе).
- `terminal` на 4-м колене принципиально неразличимы без данных за пределами выгрузки — помечаем, а не угадываем.
- Временной сигнал (`turnover_days`) сейчас на дневной гранулярности; при часовых метках отделит мулов точнее.
- Пороги перцентильные и переносимы на другой объём данных без правок кода.
